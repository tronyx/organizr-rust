# 🔀 Deviations from Organizr 2.1.5000

[← All documentation](README.md)

This version keeps the API of PHP Organizr: the paths, methods, status codes, messages and JSON shapes. This page lists every place where it differs on purpose, and why. Read it when you move from PHP, or when a script that calls the API gets an answer it didn't expect.

Each entry has an id, such as D-59. The parity tests compare every answer with a recorded PHP answer, and may differ from it only when they name one of these ids.

## 💡 In short

The differences you are most likely to meet when you move from PHP:

- **Everybody logs in again.** Sessions are random tokens, not JWTs, and the cookie is always `HttpOnly`; PHP cookies stop working at the switch (D-02, D-18).
- **A new install asks for a set-up code** from the server log, so a stranger can't claim it first (D-19).
- **Forwarding headers count only from trusted proxies.** Set `ORGANIZR_TRUSTED_PROXIES` when Organizr runs behind a reverse proxy, or every visitor looks like the proxy (D-01, D-59).
- **Changes need a same-origin request or the API key.** The static form key is gone (D-03).
- **Secrets stay secret.** `GET /config` and `GET /users` mask passwords, tokens and keys; secrets are stored encrypted with a new key (D-05, D-06, D-14, D-53).
- **Logins are harder to abuse.** Failed logins, registrations, invite codes and recovery requests are limited (D-04, D-37, D-58, D-69), and a login through Plex or Emby Connect never opens an Admin or Co-Admin account (D-127).
- **Values are checked.** Tabs, categories, groups, users and settings refuse values of the wrong kind with `422` or `409`, where PHP stored anything (D-39, D-48, D-51, D-52, D-53).
- **Text is plain text.** No HTML entities in stored or returned text (D-24).
- **Gone: running PHP code.** PHP plugins, custom PHP routes and pages, themes written for PHP's page structure, `config.php` and `cron.php` don't apply. WebAssembly extensions, built-in themes and an in-process scheduler take their place (D-40 to D-45, D-75, D-92).
- **No self-update.** Updating means pulling a new image; the update routes only check for a new release (D-23).
- **Custom JavaScript is off** until the operator starts the server with `ORGANIZR_CUSTOM_JS=1` (D-93), and custom HTML items run in a sandboxed frame unless marked trusted (D-61, D-76).
- **Custom CSS needs new names** (D-42, D-110).
- **Small format changes.** `204` answers have no body, and header names are lower-case (D-20, D-25).

What stays exactly as in PHP is listed in [Kept exactly as PHP has it](#-kept-exactly-as-php-has-it).

## 🔒 Security fixes

| Id | Change |
|---|---|
| D-01 | Client IP comes from forwarding headers only when the direct peer is in a configured trusted-proxy list. Affects "local" detection, forward-auth IP lists, the blacklist, auth-proxy login and local login bypass |
| D-02 | Sessions are opaque random tokens, not JWTs. Cookie name unchanged. PHP-issued cookies stop working at the switch. `tokenList` no longer returns other sessions' token values |
| D-03 | The static form key is replaced by a same-origin check on every state-changing request. `formKey` is accepted and ignored. State-changing GET routes keep their path and method but need a same-origin request or the API key |
| D-04 | Login attempts are limited on the server by IP and by user name. The `loginAttempts` body field is ignored; the `403 "User is locked out"` answer is unchanged |
| D-05 | `GET /users` and `GET /users/{id}` return `password` and `plex_token` as `null` |
| D-06 | `GET /config` masks every secret as `***Secure***`. The API key is shown to Admin (level 0) only |
| D-07 | `PUT /config` rejects unknown keys with `422` and cannot write bootstrap keys. Auth-proxy, API key and custom-JavaScript keys need Admin |
| D-08 | `POST /ping` and `GET /ping/{host}` only probe hosts that are configured as a tab or ping URL the caller may see |
| D-09 | Password recovery e-mails a one-time, time-limited reset link, and is rate limited. The password changes only when the link is used |
| D-10 | Backup and image file names are validated strictly (no path parts, allow-listed extensions) |
| D-11 | **Certificates are checked, except for a service reached by an IP address over HTTPS.** TLS certificates are verified unless the integration's own switch "Disable Certificate Check" is on, or the service is reached by an IP address over HTTPS. Such an address is never checked, whatever the switch says, because no certificate authority signs a certificate for an address (`is_address_over_https` in `crates/integrations/src/http.rs`; see also D-60 (5)). Reach a service by its name when the connection crosses a network that you don't trust. The importer imports these switches like every other setting, with their old values, and never turns one on (`crates/import` has no rule for them) |
| D-12 | Hard-coded third-party tokens are removed. (Later: the ipinfo token did not become a setting; `GET /ip/{ip}` asks ipinfo.io without a token, see D-82 (1).) |
| D-13 | No stack traces or PHP `exceptions` block in responses. Each response carries a request id that matches the log: the header `X-Request-Id`, a random id that the server makes for each request, also for the files of the web interface and for "not found". An `X-Request-Id` header of the client is not used. Each log line of the request carries the id, in the field `request_id` |
| D-14 | Secrets are re-encrypted with a new master key. `organizrHash` is used only during import |
| D-15 | Users can change only their own user name, e-mail, password and image through `PUT /users/{id}`. `locked`, `auth_service`, `plex_token` and `group_id` need level 1 |
| D-16 | URL fetches on behalf of non-admins (scrape, image cache) resolve the host once, check it, and connect to that address |
| D-17 | Marketplace downloads use TLS verification, a pinned commit and a hash, with path and size checks |
| D-18 | **The session cookie is always `HttpOnly`, so no script ever sees a session token.** The session cookie is always `HttpOnly`, also over plain HTTP, so a script of the page cannot read it. For the same reason `GET /token/me` returns `null` for `token` and for every `token` in `tokenList`. Each entry of that list has a new field `current`, which is `true` for the session of the request. `POST /token/validate` still returns the token that the caller sent. Approved on 2026-11-18 |
| D-19 | The set-up wizard asks for a set-up code. The server makes a random code when it starts on an install that is not set up, and writes the code to its log. `POST /wizard` needs the code in the field `setupCode`. Without the right code the answer is `403`. In PHP the first visitor of a new install becomes the Admin. Approved on 2026-11-18 |

## 🧱 Forced by the platform or by the new front end

| Id | Change |
|---|---|
| D-20 | `204` responses have no body |
| D-21 | `status` and `launch` keep their PHP-specific keys (`php`, `php_user`, `minVersion`, `dependenciesActive`, `dependenciesInactive`) with fixed values |
| D-22 | `GET /page/{page}` and `GET /organizr/{page}` serve custom pages only. Built-in page names answer with the envelope and the front-end route in `data`. PHP's form routes `/settings/*` and `/plugins/*/settings` are not built: the settings pages draw their forms from the definitions of the web application (D-96) |
| D-23 | **Updating means pulling a new image: the `/update/*` routes check for a new release and install nothing.** `/update/*` behaves as in [section 6 of the architecture](architecture.md#-6-how-php-only-features-are-kept): this application runs from a container image, and an update means pulling the new image. New route `GET /update/check`. (1) A version check asks the releases API of GitHub for the newest release of this project, in the repository of its manifest (`/repos/<owner>/<project>/releases/latest`, which leaves out drafts and pre-releases), and compares its tag (`v1.2.0` or `1.2.0`) with the version of the server by semantic versioning. The request sends no token and no cookie, its `User-Agent` is `organizr`, it has 10 seconds, and an answer over 1 MiB is not read. (2) The scheduler runs the check at `autoUpdateCronSchedule` while `autoUpdateCronEnabled` is on: the settings of the self-update of PHP are the schedule of the check. `GET /update/check` runs it at once, for Admins and Co-Admins, and only from a page of this site or with the API key (D-03). It answers `200` with `{current, latest, updateAvailable, releaseUrl}`, or `500 "The newest version could not be read from GitHub"` with the last result. A failed check keeps the result of the last check that worked. The server keeps the result in memory, so it is empty again after a start. `releaseUrl` is the page of the tag in the repository of the project; the server makes it and does not take it from the answer. (3) `GET /launch` has the new last field `update` with that object for Admins and Co-Admins, and `null` for every other caller. The page shows a notice to Admins and Co-Admins when `checkForUpdate` is on and the newest release is newer. PHP asks GitHub from the browser of an Admin at each load of the page. No e-mail is sent, because PHP has no setting for one. (4) `GET /update`, `/update/docker` and `/update/{download,unzip,move,cleanup}/{branch}` stay at level 1 and answer `409 "This install runs from a container image. To update, pull the new image and start it again"` with the data `{current, latest, updateAvailable, releaseUrl}` of the last check. They download and run nothing. PHP runs its scripts. `/update/windows` and `/update/linux` answer `409` with the texts of PHP in its container, `Your install type is not Windows` and `Your install type is not Linux`, and the same data. (5) `/update/migrate/{version}` answers `409 "The migrations of PHP Organizr do not apply to this install. The import brings the data of an install up to date"` with the same data, for every version: the migrations of PHP change files, folders and tables of PHP that this application does not have. PHP answers `200 "Ran update function for version: <version>"`, also for a version that has no migration. (6) `/update/reset/{feature}` does what PHP does: for `groupmax`, `groupidmax`, `group-max`, `group-id-max`, `group_id` and `group_id_max`, in any letter case, every tab gets the Admin as the level with the most access (`group_id_max` 0), with `200 "Ran reset update feature for <feature in lower case>"`. Another feature gets `404 "Feature not found in reset update"`. The route changes the tabs with a GET request, so it takes the check of D-03. Approved on 2026-11-18. The details (1) to (6): Decided under the standing approval of 2026-11-19. |
| D-24 | Text is stored and returned as plain text, not HTML-entity-encoded. The importer decodes existing values once |
| D-25 | Response header names are lower-case (HTTP treats names as case-insensitive) |
| D-26 | Backup archives. An archive holds the files of the data folder and a file `backup.json` that describes it. With SQLite it holds a copy of the database, as in PHP. It never holds the key for the stored secrets: in PHP the archive holds `config.php` with the key. The backup routes and their responses are unchanged. See D-74 |
| D-27 | No `PHPSESSID` cookie. The PHP application starts a PHP session on every request and needs it only during an OIDC login. The OIDC login keeps its state in a short-lived cookie of its own, set only during that login. The three no-cache headers that came with the PHP session are still sent on every answer. Approved on 2026-11-18 |
| D-28 | The switches `splash`, `ping`, `timeout` and `preload` of a tab are always `0` or `1`. PHP sends `null` for a switch that was never set, for example on the tabs of a new install. A request that sets such a switch to `null` sets it to `0`. Approved on 2026-11-18 |
| D-29 | `GET /launch` has no `status.userConfigPath`. PHP sends the path of its configuration file there, to every visitor. This application has no such file (D-45). Approved on 2026-11-18 |

| D-39 | **The tab routes check every value they store, where PHP stores anything.** `POST /tabs` and `PUT /tabs/{id}` check what they store. PHP stores any value in any field. (1) A value must be of the kind its field takes: a switch is `0`, `1`, `true` or `false`, `type` is `0` to `2`, `group_id` and `group_id_max` are `0` to `999`, `category_id` names a category, and `order` and `timeout_ms` are whole numbers. | D-48 | **The category routes check their values, keep category numbers unique, and won't delete a category that still has tabs.** `POST /categories`, `PUT /categories/{id}` and `DELETE /categories/{id}` check what they do. (1) The rules of D-39 apply to categories: `default` is `0`, `1`, `true` or `false`, and `order` and `category_id` are whole numbers. Another value gets `422 "Category <field> is not valid"`. A `category_id` that another category has gets `409 "Category category_id: <n> is already taken"`. PHP stores both, and a tab with that number then belongs to two categories. (3) A category that still has tabs is not deleted. The answer is `409 "Category name: <name> still has tabs"`. PHP deletes the category and leaves its tabs without one. Approved on 2026-11-19 |
| D-49 | **The "local network" check understands IPv6 and real network ranges.** The check for a caller on the local network reads addresses as the standards define them. (1) The address `::1`, the machine itself in IPv6, is local, and the `localIPList` setting takes addresses and networks of IPv6. PHP knows IPv4 only. (2) An entry of `localIPList` such as `192.168.1.130/25` stands for its network, `192.168.1.128` to `192.168.1.255`. PHP sets the last number to `0` and counts up from there, which gives `192.168.1.0` to `192.168.1.127`. An entry that is written as a network, such as `192.168.1.128/25`, gives the same in both.
